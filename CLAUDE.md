# Памятка по проекту

Мост между личными сообщениями ВКонтакте и Claude Code на VPS. Пользователь
пишет боту с телефона, ответ приходит туда же.

Общаться с пользователем **по-русски**. Комментарии в коде и документация —
тоже на русском, сообщения коммитов — на английском.

## На сервере бот — не главный

На том же VPS живёт **VPN (`xray`, systemd-сервис, слушает :443)**. Он приоритет.
Его безотказная работа важнее любой функции бота, и трогать его нельзя ничем:
ни конфигом, ни портом, ни пакетами, ни перезагрузкой сервера.

Что из этого следует на практике:

- **Ничего общесистемного.** Всё окружение бота живёт в его образе и в его
  папке `/opt/vk_claude_bot`. Никаких `apt install` на хосте, правок в
  `/etc`, systemd-юнитов, iptables, смены DNS. Единственное исключение —
  установка самого Docker при первой раскатке, и та спрашивает подтверждение.
- **Ресурсы поделены заранее** (`docker-compose.yml`): память и swap ограничены,
  процессорный вес занижен, `oom_score_adj: 800` — при нехватке памяти ядро
  должно выбрать бота, а не VPN. Потолки подобраны замером; поднимать их
  без нового замера нельзя.
- **Диск тоже общий.** Кончившееся место — отказ VPN, поэтому у логов, папки
  вложений и кэша сборок есть потолки. Ставя что-то новое, что пишет на диск,
  сразу ограничивай его сверху.
- **Два процесса Claude одновременно — уже риск.** Один запрос с веб-поиском
  даёт пик ~400 МБ; всего памяти на сервере 955 МБ. Всё, что может запустить
  агента параллельно с ходом (`/limits`), защищено от повторного запуска.
- **Браузер добавляет к этому пику Chromium.** Замер на сервере, ход со снимком
  страницы целиком: контейнер упирается в свой потолок 640 МБ, анонимной памяти
  303 МБ, ещё 230 МБ уходит в своп, ответ приходит за 30 секунд. То есть потолок
  держит, но с запасом в ноль: браузер поднимается по одному за раз (`_LOCK` в
  `browser.py`), гаснет сразу после снимка, и его процессу поднят
  `oom_score_adj` — если памяти не хватит, ядро возьмёт Chromium, а не Python
  с ходом разговора и не VPN.
- **Проверяя что-то на сервере, работай только со своим контейнером.**
  `docker exec vk-claude-bot …`, чтение своих логов. Ни `docker system prune`
  без фильтра, ни `systemctl restart`, ни правок вне `$REMOTE_DIR`.

## Где что лежит

```
bot/config.py         чтение .env, отбраковка шаблонных значений
bot/http.py           общая aiohttp-сессия с сертификатами certifi
bot/vk.py             VK API и цикл Bots Long Poll
bot/media.py          вложения, разбор пересланных, уборка файлов
bot/formatting.py     markdown → плоский текст, нарезка по 4000 символов
bot/sessions.py       peer_id → session_id, возраст и очистка разговоров
bot/netcheck.py       проверка адреса: не ведёт ли во внутреннюю сеть
bot/browser.py        Chromium по DevTools Protocol: текст и снимки страниц
bot/images.py         webp -> jpg и уменьшение, чтобы ВК принял фотографией
bot/vivino.py         поиск вина и рейтингов на Vivino
bot/wildberries.py    карточка товара в обход заблокированного сайта
bot/agent_tools.py    свои инструменты агента (MCP): браузер, отправка, вино
bot/claude_runner.py  вызов Claude Agent SDK, системный промпт, хук-охранник
bot/main.py           диспетчер, очередь на собеседника, команды
scripts/check_setup.py  проверка конфигурации до запуска
deploy/deploy.sh      установка и управление на сервере по SSH
```

Секреты: `.env` и `deploy/deploy.env` — оба в `.gitignore`, в репозиторий не
попадают никогда.

## Как проверять работу

Локально бот работает так же, как на сервере (Long Poll не требует белого IP):

```bash
.venv/Scripts/python.exe -m scripts.check_setup   # VK, Long Poll, белый список, ответ Claude
.venv/Scripts/python.exe -m bot.main              # запуск
```

На сервере — через `docker exec`, скрипт подаётся на stdin:

```bash
ssh -i ~/.ssh/id_ed25519 root@<host> 'docker exec -i vk-claude-bot python -' < script.py
```

Деплой: `./deploy/deploy.sh update` из **Git Bash** (PowerShell не подойдёт).
Полный список команд — `./deploy/deploy.sh --help`.

**Нельзя держать бота запущенным локально и на сервере одновременно** — два Long
Poll на одну группу растаскивают события друг у друга.

## Проверять на живом сервере, а не по документации

Этот проект несколько раз ловил ошибки, которые выглядели как успех. Порядок,
который себя оправдал: сделать → задеплоить → проверить на сервере фактическими
данными → только потом отчитываться.

Реальные случаи, стоившие времени:

- **`can_use_tool` не вызывался ни разу.** Тест «прошёл», потому что модель
  вежливо отказалась сама, а файл дополнительно закрывало встроенное
  ограничение CLI. Помог только шпион, считавший вызовы. Урок: проверять, что
  твой код *исполнился*, а не что результат похож на ожидаемый.
- **Деплой отчитывался об успехе, не применив код**: compose оставлял старый
  контейнер на новом образе. Теперь пересоздание форсировано, а `deploy.sh`
  сверяет ID образа.
- **`ps` в контейнере нет** (slim-образ) — процессы смотреть через `/proc`.
- **`/dev/tcp` в контейнере не работает** — там `dash`, а не `bash`. Проверять
  доступность сокетами из python.

## Свои инструменты агента

Кроме штатных Read/Glob/WebSearch/WebFetch у агента есть шесть своих —
`bot/agent_tools.py`, внутрипроцессный MCP-сервер. Это по-прежнему список
функций в коде бота, а не «доступ к системе»: выполнить команду ими нельзя,
и хук проверяет их наравне с остальными.

**Вино: `wine_search`.** Список названий за раз, а не одно: на фото винной
полки их десяток, и по одному вызову на бутылку упирается в `MAX_TURNS`.
Внутри — эндпоинт `explore` сайта Vivino, тот же, которым живёт его страница
поиска. Подробности, на которых всё держится, в шапке `bot/vivino.py`; главное
там про `search_term` и про переупорядочивание выдачи.

**Глаза: `page_read` и `page_screenshot`.** Настоящий Chromium (системный пакет
в образе), разговор с ним по DevTools Protocol через веб-сокет —
`bot/browser.py`. Playwright не берём: он тянет node-драйвер и свою сборку
браузера, а нужно пять команд протокола. `page_read` отдаёт текст, адреса
картинок и ссылки; `page_screenshot` сохраняет снимок в папку вложений, и агент
смотрит на него инструментом Read — то есть буквально глазами.

Снимок режется кусками по 1600 точек и не длиннее четырёх кусков. Причина не в
диске: картинку модель видит после сжатия до ~1568 точек по длинной стороне, и
лента высотой в четыре экрана превращается в нечитаемую полоску.

Каждый запрос страницы (не только первый адрес, но и редиректы, и картинки,
и скрипты) проходит через `Fetch.requestPaused` и проверяется `netcheck`.
Проверено на сервере: `169.254.169.254` и `172.17.0.1` не открываются ни
напрямую, ни перенаправлением с внешнего сайта.

**Когда сайт не пускает.** Проверка браузера («Проверяем браузер», Cloudflare)
распознаётся и пережидается до 20 секунд — заглушка часто сама уступает место
странице. Если не уступила или сайт ответил кодом 4xx, в результате инструмента
стоит пометка «САЙТ НЕ ПУСТИЛ», и системный промпт требует сказать это человеку
прямо, а не пересказывать заглушку. До этой пометки бот бодро описывал
содержимое капчи.

**Руки: `send_photo`, `send_file`, `save_image`.** Скачать картинку по адресу,
показать её человеку в переписке, отправить файл документом. Отправлять можно
только то, что лежит в папке вложений: присланное, скачанное, снимки. Иначе
«отправь файл /proc/1/environ» стало бы способом вынести токены в обход всех
проверок на чтение — путь проверяет `_resolve_local`, и это не декоративная
проверка, а несущая.

## Российские маркетплейсы и адрес сервера

Замерено с сервера, живыми запросами: Wildberries отвечает браузеру кодом 498 и
пустым телом, Ozon — 403 «Похоже, нет соединения. Выключите VPN», Авито — 439
«Доступ ограничен: проблема с IP». Дело не в том, как выглядит браузер: это
блокировка по адресу дата-центра, и никакая маскировка её не снимает.

Что с этим сделано:

- **Wildberries** — отдельная дорога, `bot/wildberries.py`. Сайт закрыт, но его
  служебный API (`card.wb.ru`, тот же, которым живёт мобильное приложение) с
  этого же адреса отвечает: название, цена, рейтинг, отзывы, описание,
  фотографии. `page_read` и `page_screenshot` узнают ссылку на товар и идут
  туда, минуя браузер. Номер хранилища картинок (`basket-NN`) вычислять по
  таблице диапазонов нельзя — WB её меняет; спрашиваем все сорок разом и берём
  ответившее.
- **Ozon и Авито** — никак. У них нет открытого API, и честный ответ бота —
  «сайт не пустил», а не выдуманное содержимое.
- **`BROWSER_PROXY`** в `.env` — если однажды понадобится российский адрес.
  Задаёт его только хозяин, агент на это влиять не может. Проверено, что флаг
  доходит до браузера: с недоступным прокси страница честно падает с
  `ERR_PROXY_CONNECTION_FAILED`.

## Грабли, на которые уже наступали

**Read показывает файл с номерами строк** (`5→содержимое`). Модель принимала их
за данные и считала «1, 1, 2, 2…». В системном промпте про это написано явно —
не удалять.

**Системный промпт заменяет штатный целиком.** Всё, что важно (формат Read,
запрет markdown, поведение с вложениями), должно быть в нём написано своими
словами.

**ВК не понимает markdown.** Ответы прогоняются через `formatting.prepare`:
снимается разметка и режется по 4000 символов, между частями пауза — иначе
флуд-контроль отобьёт хвост длинного ответа.

**Буфер SDK.** Содержимое прочитанного файла едет внутри одного JSON-сообщения;
по умолчанию буфер 1 МБ, и любое фото с телефона роняло ход. Держим
`max_buffer_size` с запасом над лимитом вложений.

**Одно действие человека — это не одно сообщение ВК.** Переслав что-то с
телефона и подписав комментарий, пользователь отправляет два сообщения подряд:
бот брался за первое, а второе получало «Занят предыдущим вопросом — отвечу
следом», и связи между ними не возникало. Поэтому перед ходом есть пауза
(`MESSAGE_MERGE_SECONDS`, по умолчанию 3 с, отсчёт от последнего сообщения):
всё, что успело прийти, склеивается в один вопрос. `_build_prompt` принимает
именно список сообщений, а не одно.

**Репост записи — это не «вложение», а вложенное сообщение.** ВК присылает его
как `attachments: [{"type": "wall", "wall": {...}}]`, и внутри лежат собственные
`text`, `attachments` (фото, ссылки) и `copy_history` для репоста репоста. Пока
`wall` разбирался наравне с видео и опросами, от пересланного поста оставалась
заглушка «содержимое недоступно» — при том, что весь текст приехал вместе с ним.
Разбирается `_walk` как ещё одна часть сообщения, наравне с пересланными.
То же с `wall_reply` (комментарий к записи).

**Транскрипт под активной сессией удалять нельзя** — следующий `resume` упадёт с
«exit code 1». Уборка по возрасту получает список активных разговоров и не
трогает их.

**`~/.claude` монтируется целиком**, а не только `projects`: рядом лежит
`.claude.json`, без которого CLI жалуется на потерянный конфиг при каждом старте.

**Домашняя папка Claude Code монтируется вне `workspace`** — из `./claude-home`.
Когда она была `./workspace/home`, та же самая папка была видна агенту как
`/app/workspace/home`, то есть **внутри песочницы чтения**: транскрипты всех
разговоров, `.claude.json`, а при входе через `claude login` — и файл с токеном.
Хук отрабатывал правильно, дыра была в раскладке томов. Урок общий: проверять
не только правило, но и что оказалось внутри его границы.

**У Vivino параметр поиска называется `search_term`, а не `q`.** С `q`
эндпоинт не ругается и не пустует — он молча игнорирует запрос и отдаёт топ вин
вообще без учёта названия. Выглядит как рабочий ответ, читается как «нашёл ваше
вино, рейтинг 4.9», а речь совсем про другую бутылку. Отсюда же требование
показывать несколько кандидатов и сверять имя с этикеткой: даже с правильным
параметром на «Tocornal Sauvignon Blanc» первым идёт «Tocornal Cabernet
Sauvignon», а нужное вино лежит десятым.

**Vivino пускает curl и не пускает «Chrome».** Из питона запрос с браузерным
User-Agent получает от WAF 403 и страницу проверки на 919 байт — стабильно, три
круга подряд, свежее соединение на запрос. Тот же запрос с `curl/8.5.0`
проходит. Логика понятна: TLS-отпечаток питона на браузер не похож, и запрос,
который представился браузером, отправляют на проверку JavaScript — питон её не
пройдёт никогда. С домашнего IP проходят оба варианта, поэтому UA не один, а
список с перебором. Мораль общая: «поставь UA как у браузера» — не всегда
маскировка, иногда это способ гарантированно получить отказ.

**Ключу сообщества нужны отдельные права на фотографии и документы.** Ключ,
которым бот читает и пишет сообщения, на `photos.getMessagesUploadServer`
отвечает ошибкой 15 «no access ... with current scopes». Ничего в остальном
поведении не меняется, и обнаруживается это ровно в тот момент, когда человек
впервые просит прислать фото. Поэтому право проверяется в `check_setup`
отдельной строкой, а инструмент отправки узнаёт ошибку 15 и говорит словами,
что надо перевыпустить ключ.

**Притворяться браузером надо целиком или никак.** Первая версия ставила
Chromium подставной User-Agent «Chrome 131», а сам браузер при этом рассылал
заголовки клиентских подсказок со своей настоящей версией 151 и словом
Headless. Такое расхождение — лучший признак автоматики, чем честная строка.
Теперь User-Agent берётся у самого браузера (`Browser.getVersion`) и правится
ровно в одном месте: HeadlessChrome -> Chrome, а рядом выставляются
согласованные подсказки. Плюс `navigator.webdriver` удаляется с прототипа (а не
подменяется геттером: часть проверок смотрит на само наличие имени), и
выправляются мелочи, которых на живой машине не бывает: ноль плагинов, одно
ядро, экран 800x600 при окне 1280x900. Проверено на bot.sannysoft.com — все
проверки зелёные. На блокировку по IP это, разумеется, не влияет никак.

**ВКонтакте не принимает webp фотографией.** А половина сайтов сейчас отдаёт
только его (Wildberries — исключительно). Без перевода в jpg «пришли фото»
превращалось в «держи непонятный файл документом». Переводит `bot/images.py`
(Pillow), он же ужимает слишком большое.

**Ленивые картинки не грузятся, пока до них не домотали.** Один прыжок в конец
страницы их не будит: на статье в Википедии половина иллюстраций оставалась
пустыми рамками, а в списке картинок было три штуки вместо одиннадцати. Мотаем
шагами, не больше десяти.

**Лимиты подписки.** Процент (`utilization`) API отдаёт только у самого потолка
(первое живое срабатывание — 90%). Точную цифру знают лишь `/usage` в Claude
Code и claude.ai; их эндпоинт `/api/oauth/usage` на долгоживущем `setup-token`
отвечает `429`. Обещать проценты в текстах бота нельзя.

**Исчерпание лимита выглядит как абсурдная ошибка** «returned an error result:
success»: CLI шлёт результат с `is_error`, `errors` пуст, в текст попадает
`subtype`. Перехватывается в `run_turn` — если был статус `rejected`, бот
объясняет ситуацию словами.

## Что может захваченный агент

Известная и намеренно оставленная дыра — подмена инструкций через содержимое.
Для модели нет разницы между указанием хозяина и текстом, который она прочитала:
инструкция может приехать внутри веб-страницы, пересланного сообщения или
присланного документа. «Захват» здесь — не выполнение чужого кода, а текст,
убедивший модель сделать что-то её же инструментами.

**Ходить по любым сайтам оставлено сознательно** — в этом смысл бота, и владелец
подтвердил, что удобство важнее. Обсуждать «а давайте уберём `WebFetch`» заново
не нужно: решение принято, вопрос стоит только про предел ущерба.

Может:

- **увести присланные вложения** — содержимое влезает в адрес запроса
  `WebFetch`, дальше оно в логах чужого сервера;
- **соврать в переписку.** Канал вывода доверенный: человек читает ответ как
  ответ бота. Фишинговая ссылка, просьба прислать пароль, подменённый ответ по
  существу. Никакой хук этого не ловит — это не про инструменты;
- **жечь лимиты подписки** — до `MAX_TURNS` шагов и до 15 минут на ход;
- **пережить страницу.** Инъекция попадает в транскрипт и подтягивается
  следующим `resume`: разговор заражён, пока не `/new`;
- **слать исходящие запросы с IP сервера** — того же, что у VPN;
- **прислать в переписку файл или картинку.** Появилось вместе с `send_photo` и
  `send_file`, и это усиление старой дыры, а не новая: канал вывода доверенный,
  а вложение убедительнее текста. Скачивается оно из интернета по адресу,
  который выбрал агент, и открывать присланный файл — уже решение человека.
  Размер ограничен, путь — папкой вложений, но содержимое не проверяет никто;
- **отрисовать в браузере чужую страницу.** Chromium в контейнере работает без
  собственной песочницы (`--no-sandbox`): ни CAP_SYS_ADMIN, ни пользовательских
  namespace там нет. Границей служит сам контейнер. Уязвимость в отрисовщике
  дала бы выполнение кода внутри контейнера — то есть то, чего у агента по
  набору инструментов нет. Считаем это принятым риском: реальная угроза здесь —
  текст, который переубедит модель, а не эксплойт нулевого дня в Chromium.

Не может: изменить или создать файл, выполнить команду, поставить пакет,
прочитать токены и `/proc`, дотянуться до хоста и до xray, залезть во внутреннюю
сеть. Не потому, что «запрещено политикой», а потому, что таких инструментов у
него нет: набор задан списком, и хук отклоняет всё, чего в списке нет.

**Всё рассуждение выше держится на одном — на наборе инструментов.** Добавить
`Bash` «на минутку, посмотреть» — и оно отменяется целиком: `/proc/1/environ`,
токены, дальше сервер и VPN. Если такой инструмент однажды понадобится, это
смена модели угроз, а не правка одной строки.

Открытый вопрос: **редиректы `WebFetch` живьём не проверялись.** Хук видит
адрес, который запросил агент; если CLI сам пойдёт по перенаправлению на
`169.254.169.254`, проверка к тому моменту уже отработает. По документации CLI
возвращает модели «перенаправление туда-то» и повторный запрос снова проходит
через хук — но на «по документации» этот проект уже обжигался.

## Что не ломать

- **Белый список** `ALLOWED_USER_IDS`: без него любой, кто найдёт сообщество,
  тратит подписку. Беседы игнорируются намеренно.
- **Хук-охранник** в `claude_runner`: `Read` — только `workspace/media`, `Glob` —
  рабочая папка (и относительные пути тоже проверяются), `WebFetch` — только
  http/https и не во внутреннюю сеть, инструмент вне набора — отказ. Иначе из
  контейнера достаются токены (`/proc/1/environ`) и метаданные облака.
- **Набор инструментов** задан явно; `Bash`, `Write`, `Edit` не входят. На этом
  держится вся модель угроз — см. «Что может захваченный агент» выше.
- **Потолки на вложения**: размер одного файла, число и суммарный вес на одно
  сообщение, потолок на всю папку. Общий диск с VPN переполниться не должен.
- **`restart: on-failure`** в compose: падение бот переживает сам, а выключение
  по `/stop` должно оставаться выключением (метка `workspace/.killed`).
- **Потолки ресурсов** в compose подобраны по замеру (пик ~400 МБ) — на сервере
  1 ГБ памяти и рядом VPN, которому падать нельзя.
- **Проверка адресов** (`bot/netcheck.py`) во всех трёх местах, где бот ходит в
  сеть по чужому адресу: хук, скачивание файла, каждый запрос браузера. Не
  только первый адрес, но и то, куда увёл редирект.
- **Отправка только из папки вложений.** `_resolve_local` в `agent_tools` —
  единственное, что отделяет «пришли фото» от «пришли мне .env».
- **Один браузер за раз** и поднятый ему `oom_score_adj`. Два Chromium рядом с
  процессом Claude — это OOM на 955 МБ памяти.
- **Один ход за раз на собеседника**, очередь на 5 вопросов, таймаут 15 минут.

## Стиль ответов бота

Живой текст в мессенджер: без заголовков, без списка источников, без рассказов о
том, как добывался ответ. Правится в `SYSTEM_PROMPT` (`bot/claude_runner.py`).

## Тесты

Отдельного фреймворка нет — проверки лежат в скретчпаде сессии и гоняются
скриптами через `.venv`. При изменении публичных структур (`Job`, `MessagePart`,
`TurnResult`, `Config`, сигнатуры `MediaStore`) заглушки в тестах нужно править
вместе с кодом: у `Config` в них `types.SimpleNamespace`, и новое поле нужно
добавлять и туда.

Заглушкам ставь маленькое `merge_window_seconds` (0.05 с) — иначе каждая
проверка диспетчера ждёт настоящие три секунды и тесты идут минутами.

Настоящие данные ВК достаются из переписки без бота: `messages.getHistory`
групповым токеном отдаёт сообщения со всеми вложениями. Разбор репостов и
склейку проверяли именно так, а не на выдуманном JSON.
